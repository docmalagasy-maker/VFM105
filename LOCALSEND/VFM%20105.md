# CAHIER DES CHARGES — VFM 105

## 1. Objet du projet

Créer un site internet permettant aux associations du district d’Ambohidratrimo de déposer un dossier en ligne auprès du VFM.

Le site doit être simple, clair, agréable à utiliser sur téléphone comme sur ordinateur, et permettre :

- la saisie des informations de l’association ;
- l’ajout de documents ;
- la description d’un projet ou d’un besoin ;
- la vérification complète du dossier avant envoi ;
- la modification des informations avant validation définitive ;
- l’enregistrement du dossier ;
- l’attribution automatique d’une référence unique commençant par **VFM-105** ;
- l’envoi automatique d’un SMS de confirmation après validation définitive.

---

## 2. Identité du projet

Nom de travail du site : **VFM 105**

Le design devra intégrer :

- le logo du VFM ;
- l’identité visuelle fournie par le responsable du projet ;
- un affichage moderne, sobre et institutionnel ;
- une interface adaptée en priorité aux smartphones.

Le logo, les couleurs définitives, les textes de présentation et les éventuelles images seront fournis séparément.

---

## 3. Parcours général de l’utilisateur

Le parcours doit obligatoirement suivre cet ordre :

**Formulaire → Prévisualisation → Modification éventuelle → Validation définitive → Enregistrement → Génération de la référence → Envoi du SMS de confirmation**

Le dossier ne doit pas être considéré comme définitivement déposé avant l’action de validation finale.

---

# 4. Formulaire de dépôt

## 4.1 Informations sur l’association

Le formulaire doit comporter au minimum les champs suivants :

### Nom de l’association
- Champ obligatoire.
- Saisie en texte libre.

### Adresse de l’association
- Champ obligatoire.
- Prévoir une zone suffisamment longue pour une adresse complète.

### Responsable principal
- Nom et prénom.
- Champ obligatoire.

### Deuxième responsable
- Nom et prénom.
- Champ facultatif.
- Le système doit permettre d’ajouter au moins deux responsables au total.

Il est souhaitable de prévoir une structure extensible permettant ultérieurement d’ajouter d’autres responsables sans refaire entièrement le formulaire.

### Activité de l’association
Zone permettant de décrire les principales activités de l’association.

Exemples :
- agriculture ;
- jeunesse ;
- sport ;
- environnement ;
- culture ;
- aide sociale ;
- développement local ;
- formation ;
- autres.

Le champ peut être une liste accompagnée d’une possibilité « Autre » avec saisie libre.

### Nombre de membres
- Champ numérique.
- Ne doit accepter que des nombres valides et positifs.

---

# 5. Coordonnées

Le formulaire doit demander les coordonnées permettant de contacter l’association.

## 5.1 Numéro de téléphone

- Champ obligatoire.
- Le numéro devra être vérifié avant validation du formulaire.
- Le système devra accepter correctement les numéros utilisés à Madagascar.
- Ce numéro sera utilisé pour envoyer le SMS de confirmation du dépôt.

## 5.2 Adresse e-mail

- Champ facultatif, sauf décision contraire ultérieure.
- Contrôle du format de l’adresse e-mail.

## 5.3 Autres coordonnées

Prévoir éventuellement une zone facultative pour :

- autre numéro de téléphone ;
- adresse complémentaire ;
- contact WhatsApp ;
- autre moyen de contact.

---

# 6. Description du projet ou de la demande

Une section spécifique doit permettre à l’association de présenter son projet.

Elle doit comprendre au minimum une grande zone de texte avec un intitulé clair, par exemple :

**« Description de votre projet, de vos besoins ou de votre demande »**

L’association doit pouvoir y indiquer librement :

- son projet ;
- ses besoins ;
- la nature de l’aide recherchée ;
- une demande de financement ;
- une demande de matériel ;
- une demande d’accompagnement ;
- toute autre information utile.

Cette zone doit accepter un texte relativement long.

---

# 7. Pièces jointes

L’utilisateur doit pouvoir joindre un ou plusieurs documents.

Exemples :

- statuts de l’association ;
- règlement intérieur ;
- récépissé ;
- document administratif ;
- présentation de projet ;
- budget ;
- document PDF ;
- document Word ;
- image ou document scanné ;
- autre pièce utile.

## 7.1 Exigences

Le système doit :

- permettre plusieurs fichiers ;
- afficher le nom de chaque fichier ajouté ;
- permettre de supprimer un fichier avant validation ;
- contrôler la taille maximale des fichiers ;
- contrôler les types de fichiers acceptés ;
- empêcher l’envoi de fichiers potentiellement dangereux ;
- conserver les fichiers de manière sécurisée.

Les limites exactes de taille pourront être définies lors du développement.

Une valeur raisonnable pourra être proposée par le programmeur, par exemple 10 Mo par fichier, sous réserve de validation.

---

# 8. Date du dépôt

La date ne doit pas être saisie manuellement par l’utilisateur.

Le système doit automatiquement enregistrer :

- la date ;
- l’heure du dépôt définitif.

La date affichée dans le dossier doit correspondre au moment où l’utilisateur effectue la validation définitive.

---

# 9. Prévisualisation obligatoire

Après avoir rempli le formulaire, l’utilisateur clique sur un bouton du type :

**« Enregistrer mon dossier »**

À ce stade, le dossier ne doit pas encore être considéré comme définitivement déposé.

Le site doit afficher une page de prévisualisation claire et soignée reprenant toutes les informations saisies.

La prévisualisation doit afficher notamment :

- nom de l’association ;
- adresse ;
- responsable principal ;
- deuxième responsable, s’il existe ;
- activité ;
- nombre de membres ;
- numéro de téléphone ;
- adresse e-mail ;
- autres coordonnées ;
- description du projet ou de la demande ;
- liste des documents joints avec leurs noms ;
- date, si une date provisoire est affichée.

La présentation doit ressembler à un véritable récapitulatif de dossier et non à un simple formulaire.

---

# 10. Choix après prévisualisation

À la fin de la prévisualisation, deux boutons doivent être clairement visibles :

## 10.1 Modifier mes renseignements

Ce bouton permet de revenir au formulaire.

Toutes les informations déjà saisies ainsi que les pièces jointes doivent être conservées autant que techniquement possible.

L’utilisateur ne doit pas avoir à recommencer son dossier depuis le début.

## 10.2 Valider définitivement mon dossier

Ce bouton réalise l’envoi définitif.

Après cette action :

1. le dossier est enregistré définitivement ;
2. une référence unique est générée ;
3. la date et l’heure définitives sont enregistrées ;
4. les pièces jointes sont associées au dossier ;
5. le SMS de confirmation est déclenché ;
6. une page de confirmation est affichée.

---

# 11. Référence automatique du dossier

Chaque dossier validé doit recevoir une référence unique.

Le préfixe imposé est :

**VFM-105**

Format recommandé :

**VFM-105-AAAA-NNNN**

Exemple :

**VFM-105-2026-0001**

Puis :

**VFM-105-2026-0002**

**VFM-105-2026-0003**

etc.

## 11.1 Règles

- La référence ne doit jamais être créée deux fois.
- Le numéro doit être généré automatiquement.
- L’utilisateur ne doit pas pouvoir le modifier.
- La référence doit être enregistrée dans la base de données.
- Elle doit apparaître sur la page finale.
- Elle doit être intégrée au SMS de confirmation.
- Elle devra être utilisable pour rechercher facilement le dossier dans l’interface d’administration.

---

# 12. Page de confirmation finale

Après validation, le site doit afficher une page confirmant clairement que le dossier a bien été reçu.

Exemple :

> Votre dossier a bien été enregistré.
>
> Référence : **VFM-105-2026-0001**
>
> Un SMS de confirmation vous a été envoyé au numéro indiqué.

La page pourra également proposer un bouton permettant de revenir à la page d’accueil.

---

# 13. Envoi automatique du SMS

Le SMS ne doit être envoyé qu’après la validation définitive du dossier.

Aucun SMS ne doit partir lors de la simple prévisualisation.

## 13.1 Exemple de SMS

> VFM 105 : Votre dossier a bien été reçu. Référence : VFM-105-2026-0001. Merci.

Le texte devra pouvoir être modifié ultérieurement sans modifier toute l’application.

## 13.2 Utilisation du numéro du responsable du projet

Le souhait est que le SMS soit envoyé à partir du numéro de téléphone personnel ou professionnel du responsable du projet.

L’architecture prévue est :

**Site internet → serveur sécurisé → téléphone Android du responsable → carte SIM → SMS au demandeur**

Le téléphone Android sert donc de passerelle SMS.

Une petite application Android ou un service équivalent devra :

- être installé sur le téléphone du responsable ;
- recevoir de façon sécurisée les demandes d’envoi du serveur ;
- envoyer le SMS avec la carte SIM du téléphone ;
- confirmer au serveur si l’envoi a réussi ou échoué.

Le programmeur devra veiller à ce qu’aucun visiteur du site ne puisse envoyer librement des SMS depuis ce téléphone.

---

# 14. Statut de l’envoi du SMS

Pour chaque dossier, le système doit au minimum conserver :

- SMS à envoyer ;
- SMS envoyé ;
- SMS échoué ;
- date et heure de l’envoi.

En cas d’échec, l’administrateur doit pouvoir identifier le problème.

Une fonction de renvoi manuel du SMS pourra être ajoutée dans l’interface d’administration.

---

# 15. Interface d’administration

Le site doit comporter une zone privée réservée aux administrateurs.

Cette partie n’est pas accessible au public.

L’administrateur doit pouvoir consulter les dossiers reçus.

Pour chaque dossier, afficher au minimum :

- référence ;
- date ;
- nom de l’association ;
- responsable principal ;
- numéro de téléphone ;
- e-mail ;
- activité ;
- nombre de membres ;
- résumé du projet ;
- pièces jointes ;
- statut du SMS.

Le programmeur doit prévoir une consultation détaillée de chaque dossier.

---

# 16. Recherche et classement des dossiers

L’interface d’administration doit permettre au minimum de rechercher un dossier par :

- référence VFM-105 ;
- nom de l’association ;
- responsable ;
- numéro de téléphone.

Il est souhaitable de pouvoir également trier les dossiers par date.

---

# 17. Statuts administratifs du dossier

Prévoir une structure permettant de faire évoluer chaque dossier avec des statuts.

Exemples :

- Reçu ;
- En cours d’étude ;
- Informations complémentaires demandées ;
- Accepté ;
- Refusé ;
- Archivé.

Cette fonction peut être développée immédiatement ou prévue techniquement pour une prochaine version.

Elle ne doit cependant pas empêcher le fonctionnement de la première version du site.

---

# 18. Base de données

Une base de données doit conserver les informations des dossiers.

Chaque dossier devra être lié à :

- sa référence ;
- ses informations d’association ;
- ses responsables ;
- ses coordonnées ;
- son projet ;
- ses pièces jointes ;
- sa date et son heure ;
- son statut ;
- l’état de l’envoi du SMS.

La base de données doit être conçue pour permettre l’ajout futur de nouvelles fonctions sans avoir à reconstruire tout le projet.

---

# 19. Sécurité

La sécurité est obligatoire car le site conservera des données personnelles.

Le programmeur doit notamment prévoir :

- connexion sécurisée HTTPS ;
- protection de l’interface administrateur ;
- mots de passe stockés de manière sécurisée ;
- validation des informations envoyées par le formulaire ;
- protection contre les envois automatisés abusifs ;
- limitation des tentatives de dépôt excessives ;
- contrôle des fichiers joints ;
- protection des clés et identifiants techniques ;
- aucune clé secrète visible dans le code public du site ;
- accès aux documents uniquement par les utilisateurs autorisés ;
- sauvegarde régulière de la base de données.

Les informations permettant de commander l’envoi des SMS ne doivent jamais être exposées dans le navigateur de l’utilisateur.

---

# 20. Protection contre les doubles validations

Lorsque l’utilisateur clique sur **« Valider définitivement mon dossier »**, le système doit empêcher qu’un double clic ou un problème de connexion crée deux dossiers.

Une seule référence doit être générée pour un même envoi.

Le SMS ne doit également être envoyé qu’une seule fois, sauf action volontaire de renvoi par un administrateur.

---

# 21. Compatibilité

Le site doit fonctionner correctement sur :

- téléphone Android ;
- iPhone ;
- tablette ;
- ordinateur.

Navigateurs principaux :

- Chrome ;
- Edge ;
- Firefox ;
- Safari.

Le développement doit être responsive, c’est-à-dire que l’affichage doit s’adapter automatiquement à la taille de l’écran.

---

# 22. Hébergement, GitHub Desktop et déploiement

Le projet devra obligatoirement être organisé autour des outils déjà utilisés par le responsable du projet :

- **GitHub Desktop** pour gérer le projet depuis l’ordinateur ;
- **GitHub** pour stocker le code source et conserver l’historique des versions ;
- **Vercel** pour héberger et publier le site internet.

Le responsable du projet possède déjà des comptes GitHub et Vercel. Le programmeur devra donc utiliser cette organisation plutôt que créer une plateforme de déploiement différente sans accord préalable.

## 22.1 Flux de travail attendu

Le fonctionnement attendu est le suivant :

**Projet sur l’ordinateur → GitHub Desktop → dépôt GitHub → Vercel → site internet en ligne**

Le programmeur devra :

1. créer ou utiliser un dépôt GitHub dédié au projet VFM 105 ;
2. configurer le projet pour qu’il puisse être ouvert et géré facilement avec GitHub Desktop ;
3. connecter le dépôt GitHub au compte Vercel du responsable du projet ;
4. configurer Vercel pour que les nouvelles versions validées du projet puissent être déployées depuis GitHub ;
5. documenter clairement la procédure pour publier une nouvelle version ;
6. éviter toute dépendance à un compte personnel du programmeur qui empêcherait le responsable du projet de reprendre la gestion du site ;
7. remettre au responsable du projet l’intégralité du code source et des fichiers nécessaires.

## 22.2 Architecture générale

L’architecture comprendra au minimum :

- le code du site web dans GitHub ;
- Vercel pour le déploiement du site ;
- une base de données sécurisée ;
- un espace sécurisé pour les pièces jointes ;
- un service serveur pour les opérations sensibles ;
- une passerelle Android pour l’envoi des SMS avec la carte SIM du responsable.

L’application Android servant de passerelle SMS devra également être livrée avec son code source complet. Son code pourra être conservé dans un dépôt GitHub séparé ou dans une partie clairement identifiée du projet, afin de faciliter sa maintenance et ses futures mises à jour.

Les clés secrètes, mots de passe, jetons d’accès et informations sensibles ne devront jamais être enregistrés directement dans un dépôt GitHub public. Ils devront être placés dans les variables d’environnement sécurisées de Vercel ou dans un système équivalent.

Le choix exact des autres technologies appartient au programmeur, mais il devra respecter toutes les fonctions décrites dans ce cahier des charges ainsi que l’utilisation de GitHub Desktop, GitHub et Vercel imposée pour la gestion et la publication du projet.

---

# 23. Comportement en cas de problème

Le site doit afficher des messages compréhensibles par un utilisateur non informaticien.

Exemples :

- « Veuillez renseigner le nom de l’association. »
- « Le numéro de téléphone semble incorrect. »
- « Ce fichier est trop volumineux. »
- « Votre dossier n’a pas pu être envoyé. Veuillez réessayer. »
- « Votre dossier est enregistré, mais le SMS n’a pas pu être envoyé. »

Si le SMS échoue après l’enregistrement du dossier, le dossier ne doit pas être supprimé.

L’échec du SMS doit être enregistré séparément.

---

# 24. Points importants à ne pas modifier

Les règles suivantes sont essentielles :

1. Le dossier doit toujours passer par une prévisualisation avant validation définitive.
2. La prévisualisation ne doit pas déclencher le SMS.
3. L’utilisateur doit pouvoir revenir modifier son dossier.
4. Le SMS ne part qu’après la validation définitive.
5. Chaque dossier validé reçoit une référence unique commençant par **VFM-105**.
6. La date et l’heure sont enregistrées automatiquement.
7. Les noms des fichiers joints doivent apparaître dans la prévisualisation.
8. Le numéro de téléphone doit être associé au dossier.
9. L’échec éventuel d’un SMS ne doit jamais provoquer la perte du dossier.
10. L’accès aux dossiers et aux documents doit être sécurisé.

---

# 25. Critères de validation du projet

Le projet sera considéré comme fonctionnel lorsque les tests suivants seront réussis :

### Test 1 — Formulaire
Un utilisateur peut remplir toutes les informations demandées.

### Test 2 — Responsable obligatoire
Le site refuse de poursuivre si le responsable principal n’est pas renseigné.

### Test 3 — Téléphone
Le site contrôle le numéro de téléphone avant de poursuivre.

### Test 4 — Documents
L’utilisateur peut ajouter plusieurs documents et voir leurs noms.

### Test 5 — Prévisualisation
Toutes les informations saisies apparaissent correctement avant validation.

### Test 6 — Modification
L’utilisateur peut revenir au formulaire sans perdre son travail.

### Test 7 — Validation
Le clic sur « Valider définitivement mon dossier » crée le dossier une seule fois.

### Test 8 — Référence
Une référence telle que **VFM-105-2026-0001** est automatiquement générée.

### Test 9 — Enregistrement
Le dossier, la date, les coordonnées, le projet et les pièces jointes sont correctement enregistrés.

### Test 10 — SMS
Le système demande à la passerelle Android d’envoyer le SMS au numéro du demandeur.

### Test 11 — Traçabilité
Le système conserve l’état de l’envoi du SMS.

### Test 12 — Administration
L’administrateur peut retrouver et consulter le dossier à partir de sa référence.

### Test 13 — Mobile
Le formulaire, la prévisualisation et l’administration restent utilisables sur smartphone.

---

# 26. Évolutions possibles

Le projet doit être conçu de façon à pouvoir ajouter ultérieurement, sans reconstruction complète :

- suivi en ligne d’un dossier grâce à sa référence ;
- notifications par e-mail ;
- plusieurs modèles de SMS ;
- changement automatique du statut d’un dossier ;
- historique des actions ;
- commentaires internes ;
- demande de pièces complémentaires ;
- génération d’un accusé de réception PDF ;
- statistiques sur les associations ;
- classement par commune ;
- tableaux de bord ;
- export Excel ou CSV ;
- gestion de plusieurs administrateurs ;
- gestion des membres du VFM ;
- communication avec d’autres modules du futur site VFM 105.

---

# 27. Résumé du fonctionnement attendu

**1.** L’association ouvre le site.

**2.** Elle remplit son formulaire.

**3.** Elle ajoute éventuellement ses documents.

**4.** Elle décrit son projet ou ses besoins.

**5.** Elle renseigne son téléphone et ses coordonnées.

**6.** Elle clique sur **« Enregistrer mon dossier »**.

**7.** Le site affiche une prévisualisation complète.

**8.** Elle choisit soit **« Modifier mes renseignements »**, soit **« Valider définitivement mon dossier »**.

**9.** En cas de validation, le dossier est enregistré.

**10.** La référence **VFM-105-AAAA-NNNN** est générée.

**11.** Le système déclenche l’envoi du SMS avec la référence du dossier.

**12.** Une confirmation finale s’affiche à l’écran.
